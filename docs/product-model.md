# Product model — Chapter 2, first increment

Status: design for review; no product entity, table, or endpoint is implemented yet.

A product describes something the retailer sells. For example, a notebook is a product; the number of notebooks currently in the warehouse is inventory.

## Product fields

| Field | Meaning | Rule or design status |
| --- | --- | --- |
| id | Internal database identity used to reference a product | Generated by the application/database; exact type to be chosen with the schema |
| sku | Stock keeping unit, a retailer's product code, such as NOTEBOOK-A5 | Required and unique, including archived products |
| name | Human-readable label, such as A5 Notebook | Required and nonblank; maximum length to be defined in the API contract |
| price | Current selling price in the retailer's single currency | Java BigDecimal; proposed nonnegative value; precision, scale, and currency still to be selected |
| active | Whether the product remains available for new business operations | Archive by setting false rather than deleting referenced records |
| lowStockThreshold | Stock level used by the low-stock report and alerts | Proposed nonnegative integer; exact boundary comparison still to be defined |

The plan requires SKU uniqueness, a name, a price, an active flag, and a low-stock threshold. Nonnegative price/threshold validation and nonblank names are proposed details for review. Constraints must eventually be enforced in PostgreSQL as well as application validation. SKU normalization, maximum lengths, and whether SKU may change need explicit decisions before implementation.

## Example

| Field | Example value |
| --- | --- |
| id | 101 (illustrative; ID type is undecided) |
| sku | NOTEBOOK-A5 |
| name | A5 Notebook |
| price | 4.50 (currency is undecided) |
| active | true |
| lowStockThreshold | 5 |

The ID identifies the database record; the SKU identifies the item in the retailer's catalog. Different products may have the same name, but must have different SKUs.

## Inventory and history

Available quantity belongs to inventory, linked to the product. This separates catalog changes (name or price) from stock operations (receiving goods or placing orders). The full relationship diagram and stock initialization procedure will be designed next. Stock uses whole units and must never become negative.

Archiving preserves a product so historical order lines can still reference it. Historical orders retain their own price snapshots: changing a product from 4.50 to 5.00 must not change an earlier order's recorded price. Proposed behavior: reject archived products in new orders while allowing existing orders to be read and cancelled under the order state rules. Detailed archive and stock-adjustment behavior will be defined in the API contract.

ADMIN manages product writes. The full read-permission matrix will be documented with the endpoints. HTTP request/response DTOs will be designed separately from persistence entities.
